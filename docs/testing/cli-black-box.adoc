= CLI Black-Box Testing Requirements

This internal document defines black-box test scenarios for the `gommitlint` command-line application.
The tests execute a built `gommitlint` binary in temporary repositories and assert only observable behavior: exit codes, stdout, stderr, files written, Git hook effects, and process behavior.

Optional background on the method and isolation rationale is in link:https://codefloe.com/itiquette/docs/src/branch/main/development/notes/cli-black-box-testing.adoc[CLI black-box testing].
This document owns Gommitlint's scenario IDs, fixtures, launcher, prerequisites, acceptance assertions, and release-gate requirements.

== Scope

In scope:

* Root command behavior, command discovery, help, version, flag parsing, suggestions, and shell completion.
* `validate` behavior for commit messages, refs, ranges, branch comparisons, count selection, rule filters, CI detection, output formats, reports, streams, and exit codes.
* `config` behavior for discovery, precedence, presets, schema, health checks, managed-source sync, and safe writes.
* `hook` behavior for local and global installation, removal, status, idempotency, coexistence, and Git workflow blocking.
* `doctor` behavior as a read-only setup inspection command.
* Main domain behavior exposed through the CLI: commit parsing, rules, checks, diagnostics, config activation, repository rules, and aggregation.
* Git-specific edge cases expected from a commit-checking tool.
* Usability, coherence, idiomatic CLI behavior, and local developer workflow quality.
* Stability, speed, concurrency, logging, color, theme, localization, preferences, and non-interactive operation.

Out of scope:

* Internal algorithms and helper-level implementation details that are already covered by domain tests.
* Screenshot or visual regression testing.
* TUI behavior. Gommitlint is explicitly non-interactive.

== Result Semantics

* `PASS`: the scenario's full observable contract was exercised and matched expectations.
* `PARTIAL`: only a smoke check or subset passed, not the complete requirement.
* `BLOCKED` (historically `NEEDS`): the scenario could not execute because a required safe fixture, tool, artifact, or sandbox was unavailable.
* `FAIL`: executed behavior violated the contract; triage whether the defect belongs to the product or harness.

A release-gate scenario is satisfied only by `PASS`. `PARTIAL`, `BLOCKED`, `NEEDS`, and `FAIL` all require follow-up before claiming release-gate coverage.

Report the exact scenario assertions, selected tier, artifacts, and unresolved requirements with each result.
Requirements, implemented tests, and successful compilation are not proof that a scenario ran or passed.

== Tracked Black-Box Harness

The link:test-environments.adoc[VM guide] defines the additional native BSD/macOS
boundary. Linux container and native VM results are reported separately.

The external-binary harness lives under `test/blackbox` with the `blackbox` build tag.
Untagged tests do not select it. Build tags select tests, not network or filesystem isolation.
For a separately authorized local run, the supported entry point is:

[source,sh]
----
just test-blackbox-container
----

The recipe is the supported entry point. Before clearing its environment, it
refuses to run when any supported CI marker is present. It snapshots current
tracked working-tree content and untracked
non-ignored files into private state. The snapshot rejects symlinks, special
files, control/traversal paths, and paths escaping the checkout; `.git`, ignored
files, caches, and ambient credential paths are not copied. A SHA-256 manifest
records every copied file and normalized executable/read-only mode.
The snapshot copies working-tree bytes, not a separate version of each staged blob.
Keep the checkout stable during capture. A manifest identifies captured content, not an atomic Git revision or authenticated publication.

The sandbox image is prepared separately, by `just test-container-prepare`, which builds it from `Containerfile.sandbox` and records the OCI archive, its SHA-256 sidecar, and a key naming the digest-pinned base, the installed packages, and a hash of the Containerfile under `bin/sandbox-image`.
That recipe is the only step that reaches a registry; it downloads the base image and its packages.
The local launcher refuses to start when the recording is absent, fails its checksum, or carries a key that no longer matches the checkout's `Containerfile.sandbox`, and names the recipe that records it.
It neither rebuilds the image nor runs against a stale one, so a tier run reaches no registry at all.
The local launcher builds and checksums the source product on the host; that build can download Go dependencies before network-denied execution.
The sandbox launcher copies and verifies the private source tree and prefetches Go modules on the host.
It then compiles and runs tagged tests inside rootless Podman with `--network=none`.
Podman 4 and 5 both work: the container's `HOME` is a plain `/home/sandbox` tmpfs with no `uid=`, `gid=` or `mode=` option, because 4.x rejects `uid=`/`gid=` on `--tmpfs` and fails the whole run with `unknown mount option`.
The mount takes the default `1777` like `/tmp` and `/run`, which excludes nobody: the container runs a single unprivileged principal under `--network=none`, `--read-only`, `--cap-drop=ALL`, `--security-opt=no-new-privileges` and private ipc/uts.

The container mounts the private source tree and module cache read-only, a writable build cache, and selected artifacts.
It does not mount the live checkout, host home, or container socket.
Capability restrictions, private state, and resource limits apply to execution, not the entire host preparation sequence.
The container timeout defaults to 15 minutes and each Go test invocation to 10 minutes.
`GOMMITLINT_EXTERNAL_RUN_TIMEOUT` and `GOMMITLINT_EXTERNAL_TEST_TIMEOUT` accept positive integer durations with `s`, `m`, or `h`.
Product tiers are not executed by active Actions workflows.

The launcher does not inherit ambient `GOMMITLINT_BLACKBOX_*` variables.
It exposes an explicit allowlist instead:

* `--source-root DIR`, `--source-manifest FILE`, and `--source-manifest-checksum FILE` provide the local launcher's already-hashed private snapshot. If omitted for a direct invocation, the sandbox launcher creates its own private snapshot before compiling tests.
* `--source-bin FILE` plus `--source-checksum FILE` stage a separately built source binary and set `GOMMITLINT_BLACKBOX_BIN`.
* `--sandbox-image FILE` plus `--sandbox-image-checksum FILE` provide the verified OCI archive loaded into a fresh private Podman store.
* `--large-history-budget DURATION` sets the validated `GOMMITLINT_BLACKBOX_LARGE_HISTORY_BUDGET`; values use `ms`, `s`, `m`, or `h`.

File inputs must be regular, non-symlink files already staged under the checkout or `RUNNER_TEMP`; a caller-provided source tree must be under `RUNNER_TEMP`.
The launcher copies inputs into its private temporary state before verification, assigns read-only or executable-only modes, and mounts only the minimum artifact directory at `/artifacts:ro`.
It never mounts the original artifact path, host home, container socket, or arbitrary host directory.

The `source` tier runs the recursive integration packages and the whole source-built black-box contract in one sandbox.
Run this local-only tier with `just test-combined-container`.
The `distribution` tier runs the same integration packages and black-box contract once per distribution listed in `test/distribution/images`, against that distribution's own packaged git, GnuPG, and OpenSSH.
Run it with `just test-combined-container-matrix`, or `just test-combined-container-matrix NAME...` for a subset; names outside the list are refused before anything runs.
Its images come from `just test-container-prepare-distributions`, which builds `test/distribution/Containerfile` over each version-tagged, digest-pinned base, installs the tools with `test/distribution/install-deps.sh`, and records archive, checksum, and key under `bin/distribution-images/NAME`, admitting only that base's registry repository.
The images carry no Go toolchain, so the local launcher compiles the tagged harnesses on the host from the same snapshot as the product, records them in a checksummed manifest, and never executes them there.
The sandbox launcher stages and verifies that harness tree like the source snapshot, mounts it read-only under `/artifacts/harness`, and runs each harness from its package directory of the read-only source with the same `--network=none` rootless Podman options as the other tiers, minus the Go module and build caches.
Each distribution runs in its own private store; a failure does not stop the others, and the run fails when any distribution fails.
The `blackbox` tier runs that same black-box contract on its own, GPG, SSH, PTY, locale, namespace, and resource-limit scenarios included.
It requires its tools and fails when they are missing; the sandbox image carries them, so no row is optional and nothing skips.
A pass covers the selected subset, not every scenario in this document.
No download token or other secret is forwarded to the launcher or sandbox.

The common exit trap attempts private-state cleanup on success and failure.
Cleanup failures still fail the run. Abrupt termination can bypass traps.
Retain approved logs and artifact identities outside temporary state when evidence is needed.

Harness rules:

* Require a separately built `gommitlint` binary.
  Execute it only as an external process.
  The harness never builds the product.
* Do not import `internal/...` product packages from black-box tests.
* Set isolated `HOME`, XDG paths, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM=1`, `GNUPGHOME`, locale, and non-interactive Git environment per run.
* Create all repositories, configs, key material, certificates, reports, and managed-source fixtures under `t.TempDir()`.
* Use run-owned local TLS fixtures for `config sync`; trust only a disposable CA exposed through the child process environment.
* Use fake sentinel secrets and assert they do not appear in stdout, stderr, vendored files, or rewritten config metadata.
* Keep GPG/SSH signing, PTY, locale, namespace, and resource-limit scenarios fail-closed; a missing tool or capability fails the tier rather than skipping the scenario. The sandbox image the tier runs in provides them.

The current harness uses the `script(1)` utility for PTY coverage.
Do not infer complete visual behavior from captured terminal bytes.

== Test Harness Requirements

The product-under-test must not access real user data, host configuration, the real keyring, or external network services.
Unexpected access is a *harness failure*, not a valid result.
Read-only runtime files and verified inputs are distinct from writable test state.
Host preparation necessarily reads source and tools and writes private build/container state. It is not itself an effect-free operation.

[cols="1,4"]
|===
|ID |Requirement

|HAR-01
|Run the separately built, checksum-verified `gommitlint` artifact as an external process. Do not import internal product packages. The harness does not rebuild the product.

|HAR-02
|Create every repository, config file, HOME, XDG directory, keyring, and temporary report path under an isolated temp directory.

|HAR-02A
|Never read or write host user/system configuration. Each run must set isolated `HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `GIT_CONFIG_GLOBAL`, and `GIT_CONFIG_NOSYSTEM=1`; all Git config writes must target files under the run temp directory.

|HAR-02B
|Never touch real host repositories, hook directories, keyrings, package-manager state, or local policy files. Fixtures may read only files created by the run itself or static repository test fixtures copied into the run temp directory.

|HAR-03
|Set `LANG=C.UTF-8`, `LC_ALL=C.UTF-8`, and `GOMMITLINT_NO_CI_DETECT=1` by default. Enable CI variables only in CI-detection scenarios.

|HAR-04
|Capture stdout, stderr, exit code, elapsed time, and touched files separately for every command.

|HAR-05
|Use real Git repositories for Git behavior. Each test must create its own repository and configure user name and email locally.

|HAR-06
|Treat network access as forbidden unless the scenario explicitly tests `config sync` with a run-owned local HTTPS test server.

|HAR-06A
|Do not reach real network or real local services. Network-dependent black-box scenarios must use a run-owned in-process fixture bound to loopback with generated content, or be recorded as blocked by the isolation policy.

|HAR-06B
|Do not fetch real remote configs, keys, package metadata, schemas, or release artifacts during black-box runs. Offline behavior is part of the contract.

|HAR-07
|Use both `--flag value` and `--flag=value` forms in the matrix for string flags.

|HAR-08
|Run representative scenarios with stdout attached to a pipe and with stdout attached to a pseudo-terminal when color or human layout is under test.

|HAR-09
|Tests that assert no writes must snapshot the repository and temp HOME before and after the command.

|HAR-10
|Performance tests must record repository size, commit count, enabled rules, wall-clock time, and machine class so regressions are explainable.

|HAR-11
|Keep product writes inside isolated test state and remove run-owned temporary state afterward. Use disposable canaries for boundary assertions. Do not read real `HOME`, XDG data, or keyrings merely to compare before/after snapshots. Cleanup failure is a failure, not proof of leaving no trace.

|HAR-12
|Prove zero egress and ingress through `.forgejo/scripts/run-external-tests-sandbox.sh`, which uses rootless Podman `--network=none`. Never modify the host firewall. No scenario may depend on the public internet.

|HAR-13
|Use only fake secrets. Any token, signing key, or `${ENV_VAR}` managed-source credential is a disposable placeholder exported solely into the isolated environment — never a real credential, and never the user's real OS keyring. If a keyring path is exercised, use an in-memory/throwaway Secret Service inside a container or VM.

|HAR-14
|A real networked run (a live managed source, a real remote, real credentials) is a separate, explicitly opt-in activity. It is never part of this plan and never runs by default or in CI.
|===

An environment-only wrapper does not satisfy the isolation requirements.
Do not substitute temporary `HOME` exports, a dead proxy, or raw tagged `go test` for the supported launcher.
For agent verification, compile the harness without running it, using an unused temporary output directory:

[source,sh]
----
(
  set -eu
  output_dir=$(mktemp -d "${TMPDIR:-/tmp}/gommitlint-compile.XXXXXX")
  trap 'rm -rf -- "$output_dir"' EXIT
  GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off \
    go test -c -tags=blackbox -buildvcs=false -mod=readonly \
    -o "$output_dir/gommitlint-blackbox.test" ./test/blackbox
)
----

This requires an available local toolchain and dependency cache. It does not execute `TestMain`, scenarios, or the shipped binary.

== Usability, Coherence, and Idiomatic CLI Behavior

These scenarios test whether Gommitlint feels like a coherent Unix-style Git tool, not just whether it returns technically correct data.
They should be run by asserting output text, but at least one release-candidate pass should also include a human review of the rendered terminal output.

[cols="1,2,4,4"]
|===
|ID |Area |Scenario |Expected observable result

|UX-01
|First run
|Run `gommitlint validate` in a normal repository with no config.
|The command succeeds or fails based on commits, not setup; output explains what happened without requiring configuration knowledge.

|UX-02
|Common local flow
|Run `config init --preset conventional`, `validate`, `hook install`, `doctor`, and a blocked invalid `git commit` in sequence.
|The commands form a coherent onboarding flow; each next step is discoverable from help, output, or docs.

|UX-03
|Error language
|Trigger missing repo, missing config, bad ref, invalid range, bad output format, bad rule name, and unwritable report file.
|Errors name the problem in user language, avoid internal package names, and include a concrete next action.

|UX-04
|Progressive disclosure
|Compare default text output, `-v`, `-vv`, `--format json`, and `--rule-help subject` for the same failure.
|Default output is concise: one finding line per violation with the inline `GLxxx` prefix, a collapsed tail beyond five violations, and the `--rule-help` hint. `-v` adds curated Expected/Actual context not already stated by the finding plus one remediation help block per rule, keeping passing commits as one-liners. `-vv` renders the complete context map per violation (deduplicated per rule) and check catalogs on passing rules. Machine output stays structured; rule help is educational.

|UX-05
|Flag consistency
|Compare equivalent root and command flags across `validate`, `config show`, `config check`, `hook status`, and `doctor`.
|Global flags behave consistently; command-specific flags do not appear where they do not apply.

|UX-06
|Input idioms
|Use files, stdin, refs, ranges, branch names, `--repo-path`, and explicit config paths in realistic shell snippets.
|Inputs use standard CLI idioms: `-` means stdin/stdout where documented, paths are literal, and no positional surprises occur.

|UX-07
|Pipe friendliness
|Pipe JSON to `jq`, plain output to a CSV parser, text output to `grep`, and stderr to a log file.
|Pipelines work without stderr scraping; stdout contains the data stream and stderr contains diagnostics.

|UX-08
|Quiet mode
|Run `--quiet` for pass, validation fail, and infrastructure fail.
|Quiet mode removes nonessential noise without hiding critical errors or changing exit-code semantics.

|UX-09
|Color and accessibility
|Run text and table output with `--color auto`, `always`, `never`, `NO_COLOR=1`, and high-contrast terminal themes.
|Color supports meaning but is not the only carrier of meaning; no-color output remains fully understandable.

|UX-10
|Terminal width
|Run human formats under narrow, normal, and wide pseudo-terminals.
|Output remains readable; long paths, commit subjects, and help suggestions wrap or truncate gracefully.

|UX-11
|Help usefulness
|A user with only `gommitlint --help`, `validate --help`, and `config init --help` should be able to create config and validate a commit.
|Help examples are executable, current, and do not require undocumented setup.

|UX-12
|Naming coherence
|Inspect command names, flag names, rule IDs, check IDs, output field names, and docs examples.
|Names are consistent: lowercase config-style rule IDs, `GLxxx` public checks, kebab-case flags, and stable JSON keys.

|UX-13
|Git mental model
|Test behavior from repo root, subdirectory, detached HEAD, feature branch, and outside repo with `--repo-path`.
|Behavior matches Git user expectations and does not depend on hidden current-directory assumptions.

|UX-14
|Recovery commands
|Trigger outputs that recommend follow-up commands, such as `config check`, `hook install`, `git branch -a`, and `git log --oneline -10`.
|Recommended commands are safe, specific, copy/pasteable, and relevant to the failure.

|UX-15
|No false interactivity
|Run side-effecting commands (`config init`, `hook install`, `hook remove`, `config sync`) in non-interactive CI mode.
|Commands never prompt; they require explicit flags like `--force` for unsafe overwrites and fail clearly otherwise.

|UX-16
|Coherent defaults
|Run a typical valid conventional commit through defaults, `preset:minimal`, `preset:conventional`, `preset:ambitious`, and `preset:secure`.
|Each preset feels intentional: minimal is low-friction, conventional is recommended, ambitious is stricter, secure emphasizes identity/signature policy.
|===

== Validation Target Selection

Target-selection precedence is part of the black-box contract because users often combine flags accidentally.

Precedence order:

`--message-file` > `--base-branch` > `--range` > `--ref` > `--count` > default `HEAD`.

The effective base can come from CI detection and outrank an explicit range, ref, or count.
Keep HAR-03's CI-disable setting for independent target-selection scenarios. Enable CI only for scenarios that explicitly test it.

[cols="1,2,4,4"]
|===
|ID |Area |Scenario |Expected observable result

|VAL-01
|Default target
|Run `gommitlint validate` in `FIX-02`.
|Exit `0`; validates `HEAD`; no config is required.

|VAL-02
|Validation failure
|Run `gommitlint validate` in `FIX-03`.
|Exit `1`; validation output identifies the failing commit or message and the failing rule/check.

|VAL-03
|Message file
|Run `gommitlint validate --message-file msg.txt` with valid and invalid files.
|Exit `0` for valid message and `1` for invalid message; no Git repository is required for message-only rules.

|VAL-04
|Stdin message
|Run `printf 'feat: add api\n' \\| gommitlint validate --message-file -` outside a Git repo.
|Exit `0`; reads exactly stdin; no prompt; no repository-required error.

|VAL-05
|Empty message
|Run `printf '' \\| gommitlint validate --message-file -`.
|Exit `65`; stderr contains a recovery hint that provides an example subject and file/stdin alternatives.

|VAL-06
|Message precedence
|Run `gommitlint validate --message-file msg.txt --base-branch main --range main..HEAD --ref HEAD~1 --count 5`.
|Only the message file is validated; branch/range/ref/count state does not affect the result.

|VAL-07
|Base branch precedence
|Run `gommitlint validate --base-branch main --range main..feature --ref HEAD~1 --count 5`.
|The base-branch comparison is used rather than the explicit range, ref, or count.

|VAL-08

|Run `gommitlint validate --range main..feature --ref HEAD~1 --count 5`.
|The explicit range is used rather than the ref or count.

|VAL-09
|Ref precedence
|Run `gommitlint validate --ref HEAD~1 --count 5`.
|The single ref is used rather than count.

|VAL-10
|Count target
|Run `gommitlint validate --count 3` in a repository with at least three commits.
|Exactly the last three commits are validated; summary commit count is `3` in machine-readable output.

|VAL-11
|Count validation
|Run `gommitlint validate --count 0`, `--count -1`, and a count greater than configured max.
|Exit `2` for non-positive counts as CLI misuse and `65` for syntactically valid counts above configured limits; errors are actionable and do not fall back to `HEAD`.

|VAL-12
|Reference not found
|Run `gommitlint validate --ref does-not-exist`.
|Exit `66`; stderr suggests listing branches or recent commits.

|VAL-13

|Exit `65`; no shell command is executed; diagnostic maps to invalid-reference behavior.

|VAL-14
|Invalid range syntax
|Run `gommitlint validate --range invalid-range-format`.
|Exit `65`; message identifies invalid range syntax.

|VAL-15
|Fallback base branches
|Run `gommitlint validate --base-branch missing,main,develop` where `main` exists.
|Uses the first existing candidate; output and diagnostics name the branch actually used when visible.

|VAL-16
|Missing base branches
|Run `gommitlint validate --base-branch missing1,missing2`.
|Exit `66`; recovery hints include branch listing.

|VAL-17
|No repository
|Run `gommitlint validate` in `FIX-01`.
|Exit `69`; stderr says to run inside a Git repository or use `--repo-path`.

|VAL-18
|Dirty worktree
|Run `gommitlint validate` in `FIX-09`.
|Validation result depends only on commits/config; staged and untracked files remain unchanged.

|SEC-05
|Permissions
|Use unreadable config files, unwritable report files, and inaccessible key directories.
|Exit codes classify no-input, no-permission, config, or unavailable failures correctly.

|SEC-06
|Terminal control characters
|Validate commits and message files containing ANSI escapes, OSC hyperlinks, carriage returns, backspaces, tabs, and other control characters in subject, body, trailers, author names, and branch names.
|Human output must not allow terminal spoofing or hidden text; machine output must remain valid and faithfully escaped.

|SEC-07
|CI annotation injection
|Validate commit messages containing GitHub workflow commands (`::error::`), GitLab section markers, newlines, `%0A`, `%0D`, commas, colons, and bracket-like payloads.
|GitHub, Forgejo, and GitLab formats escape payloads so commits cannot create forged annotations or sections.

|SEC-08
|JSON and plain escaping
|Validate messages containing quotes, backslashes, Unicode separators, newlines, commas, and invalid-looking JSON fragments.
|JSON parses as JSON. Plain output parses as RFC-4180 CSV with quoted fields, including embedded newlines. Assert logical records through a CSV parser, not line splitting.

|SEC-09
|Managed-source integrity
|Run `config sync` against local HTTPS fixtures with matching SHA-256, mismatched SHA-256, redirects, missing integrity, and changed content after first sync.
|Only verified content is written; mismatches fail without replacing the vendored file; `--check` never writes.

|SEC-10
|Managed-source secrets
|Use `${ENV_VAR}` managed-source URLs and headers containing token-like values.
|Secrets are sent only where configured, are not written to config/resolved metadata, and are redacted or absent from stdout/stderr/logs.

|SEC-11
|HTTPS and header policy
|Configure managed sources with custom headers over rejected `http://` sources and a run-owned local HTTPS fixture.
|Headers over insecure URLs are rejected before fetch; safe local HTTPS behavior follows documented policy.

|SEC-12
|Hook installation safety
|Install and remove hooks in repositories with symlinked hook paths, read-only hook directories, existing custom hooks, and global Git config pointing outside isolated HOME.
|Gommitlint preserves unrelated hooks even with `--force`, rejects unsafe hook paths, and reports permission failures clearly. Only existing Gommitlint-managed hooks are replaceable through that flag.

|SEC-13
|Global state isolation
|Run global hook and XDG config commands with isolated `HOME`, `XDG_CONFIG_HOME`, `GIT_CONFIG_GLOBAL`, and `GIT_CONFIG_NOSYSTEM=1`.
|Only the isolated test environment changes; user/system Git config is not read or modified.
|===

== Minimum Release Gate

A release candidate should not ship unless these black-box groups report `PASS` on at least one supported Linux architecture:

* `CLI-01` through `CLI-12`
* `UX-01` through `UX-16`
* `VAL-01` through `VAL-18`
* `RULE-01` through `RULE-09`
* `DOM-01` through `DOM-40`
* `OUT-01` through `OUT-17`
* `CFG-01` through `CFG-11`
* `GIT-01` through `GIT-12`
* `HOOK-01` through `HOOK-09`
* `DOC-01` through `DOC-04`
* `CI-01`, `CI-05`, and `CI-06`
* `STAB-01`, `STAB-02`, `STAB-04`, `STAB-06`, and `STAB-08`
* `SEC-01` through `SEC-13`
* `DOCS-01` and `DOCS-02`

This membership is a requirement, not proof that the ordinary `blackbox` tier exercises every listed case.
Some listed color, terminal, key, or platform assertions need separately recorded evidence.
Do not convert a missing assertion or excluded test into `PASS` because the selected test process exited zero.

The remaining scenarios should run locally during pre-release hardening because they require optional tools, test keys, local TLS fixtures, package images, or more expensive environments.
