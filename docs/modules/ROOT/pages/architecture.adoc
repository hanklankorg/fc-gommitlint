== 1. Introduction and Goals

Gommitlint validates Git commit messages against configurable rules.
It runs as a CLI tool, Git hook, or in CI/CD pipelines.

=== Quality Goals

These are design goals, not benchmark results or guarantees for every invocation.

|===
| Priority | Goal | Motivation

| 1
| Correctness
| Validation rules must produce accurate, deterministic results

| 2
| Usability
| Clear error messages guide developers to fix issues

| 3
| Extensibility
| New rules registered through the catalogue and factory without redesigning validation coordination

| 4
| Performance
| Sub-second validation for typical repositories

| 5
| Portability
| One binary with in-process SHA-1 repository access. SHA-256 repository access requires system Git
|===

=== Stakeholders

|===
| Role | Expectation

| Developer
| Clear feedback on commit message issues

| Team
| Consistent commit standards across team

| CI/CD Pipeline
| Machine-readable output, proper exit codes

| Contributor
| Understandable codebase for adding rules
|===

== 2. Constraints

|===
| Constraint | Background

| Go 1.27.2+
| The module's `go` directive is the toolchain authority (see `go.mod`)

| Two repository adapters
| go-git for SHA-1 repositories. A detected SHA-256 format selects system Git at runtime

| Unix conventions
| stdout for results, stderr for logs

| XDG compliance
| Config in `$XDG_CONFIG_HOME/gommitlint/`

The repository opener attempts object-format detection through system Git.
A detection error, empty result, or unrecognized format falls back to go-git. This fallback is not proof of SHA-1 format.
See xref:sha256-repositories.adoc[SHA-256 Repositories] for adapter and distribution limits.

== 4. Solution Strategy

=== Hexagonal Architecture

Gommitlint implements the Ports and Adapters pattern (Hexagonal Architecture)
as defined by Alistair Cockburn.
The core coordinates business rules through interfaces and dependency functions instead of importing concrete Git or CLI adapters.
That separation makes dependencies replaceable. It does not make every core call pure or independent of host state.

==== The Hexagon

The application core consists of `internal/app` and `internal/domain`.
Dependencies point inward from adapters through application services to the
domain. Inside the core:

* Use-case coordination in `internal/app/validation` and `internal/app/hooks`
* Rule logic and domain models in `internal/domain`
* Domain types (Commit, ValidationError, ValidationResult)
* Port interfaces and dependency functions consumed by the core
* No adapter or third-party framework imports in the current core packages

Core validation calls the supplied logger and repository capabilities.
Application services also call injected readers, rule builders, and clocks. The default validation clock is `time.Now`.
Within the domain, worker selection reads `runtime.GOMAXPROCS`, and relative-path checks use `filepath.Abs`.
The latter can depend on the current working directory.
The intended boundary is explicit coordination and isolated effects, not a universal absence of effects or ambient state.

==== Actors

Actors are external entities that interact with the application:

*Driver Actors* (left side - trigger interactions):

* Developer running CLI
* Git hooks (commit-msg, pre-push)
* CI/CD pipelines
* Test harnesses

*Driven Actors* (right side - application calls them):

* Git repository (provides commits)
* Configuration files (provides settings)
* Filesystem (provides keys)
* Spell checker (provides corrections)

==== Ports

Ports are interfaces at the application-core boundary, defined by the package
that consumes them:

*Driver Ports* (API - how actors use the application):

* `validation.Service.Validate(ctx, request) → Report`
* Hook lifecycle operations on `hooks.Service` and pre-push introduced-commit
  selection in `hooks.SelectPrePushCommits`

*Driven Ports* (SPI - what the application needs):

* `Repository` - commit retrieval, branch analysis
* `Logger` - diagnostic output
* `KeyProvider` - key file access
* `SpellChecker` - text correction
* `validation` dependency functions - repository opening, rule building, and message reading
* `hooks.Store` and hook dependency functions - filesystem and Git configuration operations

==== Adapters

Adapters translate between technology and ports:

*Driver Adapters* (use driver ports):

* `adapters/cli` - urfave/cli framework → application services
* Test adapters - test cases → validation functions

*Driven Adapters* (implement driven ports):

* `adapters/git` - go-git library → Repository interface
* `adapters/gitcli` - system Git CLI → Repository interface for SHA-256 repositories
* `adapters/signing` - public-key parsing and metadata for the active rule; also contains a verifier not wired into production validation
* `adapters/logging` - zerolog → Logger interface
* `adapters/spell` - golangci/misspell → SpellChecker interface
* `adapters/configuration` - koanf → config file loading
* `adapters/output` - formatters → text/plain/JSON/GitHub/GitLab/Forgejo/table/SARIF output

==== Dependency Direction

All dependencies point inward toward the domain:

[,text]
----
Adapters ──────────────▶ Application ──────────────▶ Domain
 (I/O and frameworks)    (use-case coordination)    (business rules and ports)

• Adapters may depend on application and domain packages
• Application services may depend on domain packages, never adapters
• Domain packages depend on neither application nor adapters
----

In the *Configurable Dependency Pattern*, domain or application consumers define interfaces (ports).
At startup, the composition root (CLI) injects concrete implementations (adapters).
`adapters/cli` wires the command dependencies, while `cmd/gommitlint` owns the process lifecycle.
Two focused construction packages also import sibling adapters: `adapters/repository` selects go-git or system Git, and `adapters/rulefactory` builds rules with signing and stemming capabilities.
The depguard rules in `development/golangci-lint/golangci.yml` name these composition exceptions.

Driven adapters may import application-owned contracts and their request/result types; importing a consumer's port does not reverse the runtime dependency.
Validation and hook ports stay beside their consumers in `app/validation` and `app/hooks`.
Other adapter-to-adapter imports are limited to the explicitly shared support packages: `fileops` (bounded file reads), `filesystem` (path/discovery helpers), `gitrefs` (reference construction), and `output` (report writers).
Keep new exceptions cohesive and documented in the rule rather than introducing a general shared-ports package.

Import guards check package dependencies, not individual effects.
Gommitlint's current core does not need `net/http` or `syscall`, so its local guards reject those imports; standard-library types or constants alone are not network or system-call execution.
Review the actual responsibility before adapting these rules for another consumer.
Add layers when policy, coordination, and external mechanisms need separate owners, rather than counting external dependencies.

Package tests follow their owners: validation and hook workflows beside application code; Git, signing, configuration, and filesystem behavior beside adapters.
Repository-wide workflow and launcher contracts live in `test/policy`; cross-package scenarios in `test/integration`; public binary scenarios in `test/blackbox`.
Policy tests run with ordinary untagged tests; integration and black-box scenarios retain their existing build tags and guarded execution tiers.
Tests are organized by responsibility and execution tier, not parallel hexagonal layers.

==== Why No `ports/` Directory?

Following Go's idiomatic approach, ports are defined where they are consumed:

* `internal/domain/commit.go` defines the repository capability interfaces
* `internal/domain/rules/interfaces.go` defines `KeyProvider` and `SpellChecker`
* `internal/app/validation/service.go` defines validation dependency function types
* `internal/app/hooks/service.go` defines `Store` and hook dependency function types

This follows Go's principle: *"Accept interfaces, return structs."*
The domain or application consumer defines the interface it needs, not the provider.
See <<_adr_7_consumer_defined_interfaces,ADR-7>> for rationale.

==== Benefits Realized

|===
| Benefit | How Gommitlint Achieves It

| *Testability*
| Domain tested with mock adapters (in-memory git, fake spellcheck)

| *Flexibility*
| Multiple output formats without changing validation logic

| *Maintainability*
| Change go-git version without touching domain

| *Technology agnostic*
| Current domain packages import only the standard library and other domain packages, not third-party libraries or adapters
|===

=== Key Architectural Principles

|===
| Principle | Implementation

| Pure functions
| Keep rule decisions deterministic for fixed inputs. Validation can call effectful dependencies, including the logger

| Value semantics
| Prefer returned values. Go structs, slices, and maps are not inherently immutable

| Explicit dependencies
| Inject operational dependencies. Package-level error values and compiled patterns still exist

| Interface segregation
| Small, focused interfaces (Repository, Logger, etc.)

| Consumer-defined interfaces
| Domain or application consumers define what they need. Adapters provide it
|===

For example, `ValidationError.WithContextMap` copies the context map before adding entries.
In contrast, `NewCommitWithSignaturePayload` retains the supplied byte slice. Copying the containing struct does not copy that slice's backing array.
Callers must preserve ownership rather than assume deep immutability.

== 7. Deployment View

Gommitlint has no server or daemon. Each invocation is a short-lived CLI
process that reads configuration and repository data, prints results, and
exits. SHA-1 repositories are read in process through go-git. SHA-256
repositories go through system Git.

=== Runtime contexts

Local developer workstation::
Users run `gommitlint validate` directly or through installed Git hooks.
State is not confined to the repository's `.git` directory or configuration files.
Selected report paths, user-wide hooks, managed-source copies, CI summaries, and crash reports can use other locations.
Hook installation and removal are separate filesystem and Git-configuration mutations, not validation-only operations.

CI/CD runner::
A pinned binary release executed against a fetched repository. SHA-1 repositories
use the go-git adapter. SHA-256 repositories use the system-Git adapter, chosen
at runtime from the detected object format. Exit codes drive the build verdict.
Structured output feeds downstream reporting.

=== External dependencies at runtime

* The Git repository under inspection, accessed through read operations in the selected adapter. This is not a filesystem sandbox.
* System Git for SHA-256 repositories.
* Optional GPG/SSH public-key material from `crypto_signature.key_directory` for independent key-inventory policy. It is not bound to the commit signature.
* Only explicit `config sync` fetches configured managed sources, including in its check and dry-run modes. Ordinary loads use local copies.
* System Git uses the inherited environment and Git configuration. Its process is not an isolated runtime.

=== Distribution

The current unreleased workflow targets a Cosign-signed checksum manifest,
Cosign-signed image/evidence artifacts, and GPG distro-package sidecars.
Historical releases used the signer stored in their tagged workflow and must
not be attributed to the current ci-policy key. Signer ownership, missing
historical trust routes, and verification are documented in
xref:verify.adoc[Verifying Gommitlint Artifacts].

== 8. Crosscutting Concepts

=== Configuration Resolution

[,text]
----
Discovery: defaults ──▶ XDG global config ──▶ project config
Explicit:  defaults ──▶ --config file and its imports
Ignored:   defaults only
----

`--config` bypasses discovered global and project files. Runtime flags are
applied after the selected load mode.
Discovery selects at most one user file and one project file, not every supported extension.
Project settings can override user settings. The user file is not an enforced policy floor.
Explicit-file and defaults-only modes bypass discovered configuration.

See xref:usecases/config-resolution.adoc[Config Resolution Use Case] for details.

=== Rule Activation Priority

. *Explicitly disabled* → Never runs
. *Explicitly enabled* → Runs when not explicitly disabled; this opts into default-disabled rules
. *Default disabled* (3 rules: jirareference, identity, linearhistory) → Skips unless enabled
. *Default enabled* (7 rules) → Runs unless disabled

Check-level activation is a separate layer. `checks.enabled` can activate its parent rule, while `checks.disabled` filters diagnostics after execution.
An explicit parent-rule disable still vetoes activation.
Allowed fixup/squash/amend commits, or disabling GL901, can skip all commit rules, including signature and identity checks.
Repository rules can still fail. An enabled rule is not proof that every selected commit was checked by it.

=== Error Model

`ValidationError` contains `Rule`, `Diagnostic`, `Message`, and `Context`.
It does not contain top-level `Code` or `Help` fields:

* *Rule*: Which rule failed
* *Diagnostic*: Public `ID`, internal `Reason`, `Category`, and `Summary`
* *Message*: Human-readable description
* *Context*: Key-value details (expected/actual)
* *Help*: Formatter-generated guidance, not a stored `ValidationError` field. Human output detail depends on verbosity

=== Output Streams

Following Unix conventions:

* *stdout*: Results (validation output, config display)
* *stderr*: Diagnostics (logs, system errors)

== 9. Architectural Decisions

=== ADR-1: Hexagonal Architecture

*Decision*: Domain at the center with pure business logic, application services
for use-case coordination, and adapters at the edges for I/O.

Dependencies point from adapters to application services to domain packages.
Domain and application packages do not import adapters.

=== ADR-2: Pure Logic and Value Semantics

*Decision*: Keep validation deterministic, pass dependencies explicitly, and
return new values instead of mutating shared state. I/O remains in adapters or
application orchestration.

This is the design intent. Core port calls, host-dependent helpers, and shallow slice/map copies need explicit review under this policy.

=== ADR-3: Two-Phase Hook Validation

*Decision*: Run message rules in `commit-msg` before the commit exists. Run the
signature metadata policy in `pre-push` over the commits introduced by the
push. The latter does not add cryptographic signer verification.

See xref:usecases/hook-lifecycle.adoc[Hook Lifecycle Use Case] for details.

=== ADR-4: Two Rule Interface Types

*Decision*: `CommitRule` receives commit data; `RepositoryRule` receives Git
context. Message-file validation can therefore run without a repository, while
`branchahead` remains repository-scoped.

=== ADR-5: Exit Code Classification

*Decision*: Separate validation, usage, input, environment, software,
permission, and configuration failures using POSIX and BSD `sysexits.h`
conventions. The process mapping is owned by `resolveExitCode` in
`cmd/gommitlint/main.go`. `internal/domain/errors.go` classifies validation
reasons.

The full numeric contract lives in xref:cli-conventions.adoc[CLI Conventions].

=== ADR-6: Bounded Untrusted Input

*Decision*: Use bounded input handling rather than assume repositories and configuration are small or trusted.
The go-git range walk (`commitsInRange`, used for `--range` and branch-ahead counts) loads at most 100,000 commit objects.
Like `git rev-list from..to`, it walks newest first and stops once no remaining commit can belong to the range, so the bound covers the requested range and its boundary rather than the depth of the history.
Committer dates that run backwards can make it include a commit a full ancestry walk would exclude, as git's own walk can.
This threshold applies to that walk, not every repository traversal or the system-Git adapter.

Configuration parsing caps each input file at 1 MiB. Imports have a separate nesting-depth limit.
These limits are independent of `--count`. They are not whole-process CPU, elapsed-time, or memory budgets.

=== ADR-7: Consumer-Defined Interfaces

*Decision*: Define minimal interfaces in the domain or application package that
consumes them. Adapters satisfy those interfaces directly. There is no shared
`ports/` package, wrapper type, or adapter base class. This keeps dependency
direction visible in package imports and avoids provider-owned abstractions.
