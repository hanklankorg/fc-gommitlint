`rules.enabled` adds rules to catalog defaults; it is not an exclusive allow-list.
`rules.disabled` takes precedence, and runtime rule filters can narrow the resulting selection.
The signature rule is enabled by default, but `crypto_signature.required` defaults to `false`, so unsigned commits are not rejected by default.
Commit selection and ignore policies determine coverage; default-enabled rules do not imply that every commit was checked.

=== Check IDs

Rules are execution/configuration groups.
Checks are public diagnostic IDs attached by a rule, dispatcher, or CLI error-adaptation path.
JSON exposes the more specific internal reason as `diagnostic.reason`.
Report formatters expose `GLxxx` for report entries.
Recovery/setup errors use the same metadata internally for classification, but render actionable recovery messages.

==== Check Catalog

Use `checks.enabled` / `checks.disabled` to select individual rule-backed `GLxxx` checks.
For rule-backed rows, use `rules.enabled` / `rules.disabled` to select whole rules by the rule ID shown in *Source*. Dispatcher sources such as `fixup` and `validation` are not rules.

The *Specific Controls / Inputs* column lists settings, CLI inputs, or external prerequisites that can change that specific check's behavior.
`checks.enabled` selects a check and its parent rule. It does not change the behavior settings listed in *Specific Controls / Inputs*.
`GL901` is the only dispatcher check controlled by `checks.disabled`.
Other `GL900`-range diagnostics identify required runtime/input failures and cannot be enabled or disabled through `checks.*`.

`No per-check tuning` means fixed behavior inside the source rule.
If you do not want it enforced, disable the rule-backed `GLxxx` check or its parent rule.
Rows marked as reserved or adapter-facing are registered public IDs, but the current normal rule path does not produce them directly.

Parent-rule disabling still takes precedence over `checks.enabled`, and `checks.disabled` removes a check even when it is also enabled.
Enabling one check does not restrict other default-enabled rules or checks.
When a parent is activated only through `checks.enabled`, only the selected checks from that parent are retained.
Use the resolved rule/check set rather than treating either enabled list as the complete policy.

Check filtering applies to diagnostics returned by the parent rule, not to independent per-check execution.
The rule can perform prerequisite work or return early before later checks are reached.
Selecting a diagnostic ID is not a sandbox or proof that every named condition was evaluated.

=== Commit type (`conventional`)

Validates commit messages follow conventional commit format: `type(scope): description`

**Default types:** `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, `test`

`conventional.types` and the other conventional settings can change the accepted forms.
The examples below describe conventional syntax, not complete validation results for every enabled rule.

**Examples:**
----
✓ feat: add user authentication
✓ fix(api): resolve login timeout issue
✓ docs: update README installation steps
✗ Add user auth (missing type prefix)
✗ feat add auth (missing colon)
----

=== Subject

Validates commit subject line format, length, and content requirements.

**Requirements:**

* A nonempty subject within `message.subject.max_length` (default: 100 characters).
* No suffix from `message.subject.forbid_endings`.
* Imperative mood when `message.subject.require_imperative` is enabled; product defaults enable it.
* The configured `message.subject.case`; `auto` chooses lowercase for conventional mode and sentence case otherwise.

The following examples assume non-conventional subject handling with imperative mood required.
Selecting only `--rule subject` does not disable conventional awareness when the effective configuration still enables `conventional`.

**Examples:**
----
✓ Add user authentication system
✓ Fix memory leak in parser
✗ Added user authentication (past tense)
✗ Fix memory leak. (trailing punctuation)
----

=== Sign-off (`signoff`)

Checks the configured count, format, placement, and duplicate-email conditions for sign-off trailers.
It does not authenticate the signer, establish email ownership, or determine whether a contributor has the legal rights stated by the DCO.
`message.body.min_signoff_count = 0` disables these sign-off checks.

**Required format:** `Signed-off-by: Your Real Name <your.email@domain.com>`

**Examples:**
----
✓ Signed-off-by: John Doe <john@example.com>
✓ Signed-off-by: John <john@example.com>
✗ Signed-off-by:John Doe<john@example.com> (missing spaces)
----

These are trailer-format examples only.
The current pattern accepts a one-word name and does not enforce a given-name/family-name convention.
Duplicate detection compares extracted emails case-insensitively, as the identity rule does, and never compares names; it does not authenticate identities.

=== Signature (`cryptosignature`)

Checks commit signature metadata. This rule does not cryptographically verify
the commit payload against a key, determine who signed it, authorize a signer,
or detect replay.

The rule ID is `cryptosignature`; its configuration section is `gommitlint.crypto_signature`.
Do not use `cryptosignature.*` as configuration paths.

**Validation modes:**

* `required: true` - Signature must be present
* `verify_format: true` - Validate signature structure
* `require_gpg: true` - Only GPG signatures allowed
* `require_ssh: true` - Only SSH signatures allowed
* `key_directory` - Require an eligible public key of the declared signature type

Unsigned commits skip later type, format, and key-inventory checks unless `required: true` rejects their missing signature.
Enabling `GL501` alone does not change `required` to true.
One eligible inventory key must satisfy the applicable constraints; this is not a requirement that every key passes them.

Key-directory policy is independent of the signature block.
`allowed_signers` compares fingerprints and emails case-insensitively, but full user IDs case-sensitively.
It does not bind a matching key to the commit signature.
For cryptographic verification, use an independently trusted Git verification setup or forge signature policy.
See xref:{up}usecases/crypto-verification.adoc[Signature Policy] for the exact boundary.

=== Commit body (`commitbody`)

Validates commit message body format and content.

**Configuration:**

* `required: true` - Body must be present
* `min_length: N` - Minimum character count of a body that is present (0=disabled); it does not by itself require a body
* `max_line_length: N` - Maximum characters per line (default: 72, 0=disabled); lines holding a single unbreakable token such as a URL, and identity trailers such as `Signed-off-by: Name <address>`, are exempt
* `allow_signoff_only: true` - Allow body with only sign-off trailers

These fields belong under `gommitlint.message.body`.

=== JIRA reference (`jirareference`)

Validates JIRA issue references in commits.

**Valid positions:**

* Subject scope: `feat(PROJ-123): description`
* Subject end: `feat: description PROJ-123`
* Body: `Refs: PROJ-123`

Accepted positions depend on `jira.require_in_subject`, `jira.require_in_body`, and the other JIRA settings.
Do not assume every listed form satisfies every configured mode.
A key must stand on its own: `[PROJ-123]` and `(PROJ-123)` are keys, `xPROJ-123` and `PROJ-123abc` are not.
With `jira.project_prefixes` set, only a key with a listed prefix is a reference, so `SHA-256` in a subject no longer satisfies the rule.

=== Branch Ahead (`branchahead`)

Validates current branch is not too far ahead of reference branch.

**Configuration:**

* `max_commits_ahead: N` - Maximum allowed commits ahead (default: 10)

Use `--base-branch` to choose the base branch at runtime.

=== Linear History (`linearhistory`)

Rejects commits whose parsed metadata marks them as merges, normally because they have more than one parent.
It does not infer merge status from the subject or enforce one particular history-editing workflow.

**Common merge subjects, not matching patterns:**

* `Merge branch 'main' into feature`
* `Merge pull request #123 from user/branch`

A non-merge commit with one of these subjects is not rejected by this rule merely for its text.
Follow the repository's approved history policy when resolving a failure.
Do not rewrite or force-push shared history without explicit authorization.

=== Identity

Checks the commit author email. It does not inspect the committer email or a
signature identity. Matching is case-insensitive. An empty allow-list permits
all author emails.
The author field is commit metadata, not authenticated proof of authorship.

**Configuration:**

* `allowed_authors: ["developer@example.com"]` - Allow an exact author email
* `allowed_authors: ["*@company.com"]` - Allow any author email in a domain

=== Spelling (`spell`)

Spell checking for commit message text.

**Configuration:**

* `locale: both` - Dictionary locale (`both`, US, UK, GB; default: `both`)
* `ignore_words: [api, json]` - Custom words to skip
